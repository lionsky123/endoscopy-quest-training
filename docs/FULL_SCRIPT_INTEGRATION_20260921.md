## 已接入的实际入口

`VisitorInstaller` 的 VR 分支现在创建 `FullScriptJourneyRuntime`，不再直接创建只有洗消地图的 composition。配置缺失会报错，不会静默回退到旧单房间。

实际路径为：医院大厅 → 办公室 → 储存库 → 候诊区 → 诊疗区 → 清洗消毒室 → 办公室汇总。前五个空间为明确标注的开发灰盒，洗消空间沿用原模型、哈希和路线。保留原开场手掌印记、安小卫对话组件；开场说明“四位一体”原则及完整路线。切房后不重复开场。

房间内跟随精灵实际走动；结束阅读只启动去房门的引导。在入口门区内（开发判定半径0.85m）真实手部近触目的地按钮，才可提交切换。按钮不能在远处触发，进入门区本身不会自动切房。可回查已访房间，仍按主线游标续接尚未到访的下一房间。

所有房间共用一次首次追踪对齐和一个追踪事件生命周期。开发地图的门口复用同一固定物理位置；转场不改头手Transform，不在每个房间重置trackingSpace。进入不同房间后仍按原固定世界规则步行。场地大小未知，没有自动边界适配或安全区可达性保证；部署前必须验证完整步行范围。

## 转场和共享界面生命周期

转场顺序：锁定输入/精灵暂停 → 淡出 → 释放旧房间及课程运行时 → 下一帧创建目标房间 → 等可靠追踪 → 提交旅程ticket → 淡入 → 恢复交互。没有调用构建/安装/设备启动。

目标资源失败时先恢复原房间，不改已访集合；近触恢复后才能再试。追踪丢失不提交目的房间。重试界面固定在过渡遮罩前；房间恢复仍需可靠追踪。

实际联调发现：原`KnowledgeMiniGameCompletionBinding.Dispose`和composition释放了场景共享的`KnowledgeMiniGameFrontend`，下一房间再次Configure会抛ObjectDisposedException。现区分共享界面所有权，房间结束仅解绑/Unconfigure，场景最终销毁才Dispose；旧单房间调用保持原默认所有权。回归测试覆盖真实加载、失败恢复、再切换以及重复创建新运行时。

## 办公室电脑切片

按新稿S1的“到电脑前、触碰电脑、放大界面”落实：到站后出现电脑交互屏幕；必须近触终端，才出现固定在展开位置的可读界面。逐项查看以下四组字段：

1. 诊疗日期。
2. 患者标识与内镜编号。
3. 清洗消毒起止时间。
4. 操作人员姓名。

当前界面使用虚构阅读样例，不是新稿截图的逐字转录，不是真实医院记录，也不连接医院系统。示例值和处理时长不能当临床标准。四组已查看标记仅是阅读记录：在同次运行复访保留，重启/重选模式清空；不算OF-01完成，也不算独立判断正确。正式数据集、按镜号/日期调取、字段错配和完整性判断、5.2/5.3等监测材料仍未交付。
