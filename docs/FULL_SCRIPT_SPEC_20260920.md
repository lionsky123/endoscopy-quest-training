## 4. 房间切换与实际场地

### 4.1 切换入口与过程

已确认交互（D02）：完成房间学习或明确处理未完成项后，小精灵引导用户实际走到房门，在门口近触“前往××”按钮，再淡出切换。房间总结页只启动去门口的引导，不能直接切换房间；门口按钮须位于当前可走活动区内。计时结束、视线停留或接近门口均不能自动切换。

教学关门与房间切换是不同操作：新稿N04通过门体真实关闭状态完成教学；用于离开的门口按钮只提交房间切换请求，不替代关门，也不因开关门动作自动换房。门口按钮与把手须有清楚的交互分区，防止一个手势同时关门和离开。

切换过程必须满足：

1. 同一时刻仅受理一次请求；确认目的房间存在、资源可用、路径与模型匹配，在本次运行的内存中保留当前会话及恢复检查点，不写跨重启进度。
2. 关闭原房间主面板、全景、取景窗和视频；取消真实抓取并收起房间内工具，不能携带旧交互回调进入新房间。业务证据记录继续保留。
3. 淡出到不展示空间跳变的过渡画面，加载并验证目标房间；只在过渡阶段进行进入姿态对齐，禁止可见状态下拖动或旋转用户镜头。
4. 可靠头部追踪、头手一致的定位、有效地面和活动区验证通过后，一次性进入目标房间的入口状态；真实站立高度、俯仰和侧倾保持不变。
5. 淡入，显示目标房间名称和本房间任务，再开放手部输入、小精灵和到站检测；此前的未结束触碰必须先解除，不能穿透成下一页点击。
6. 失败时保留当前内存进度，提供重试或返回可恢复房间的入口；不得黑屏卡死、误记目的房间完成或自动跳过缺失内容。

实现必须区分两类坐标变化：系统追踪原点改变时的补偿，以及用户主动跨房间时的进入对齐。当前 `VirtualRoomTrackingOrigin` 只面向单房间首次对齐，不能在多个房间分别重复订阅同一事件、叠加补偿或让旧补偿撤销新进入姿态。

### 4.2 可走范围与场地适配

房间切换不改变人在现实中的位置，也不把人自动带回实际活动区中心。若人在边缘切换，却把他当作处于一块新场地中心，下一次引导仍可能越界。

每个房间需发布：入口、活动区边界、必须到达的观察位、站点间路线、站立及伸手余量，以及与部署场地的对应关系。不能仅检查小精灵路径无碰撞就宣称玩家路线可用；虚拟碰撞体也不能阻止玩家身体穿过虚拟墙。

- 实际移动与虚拟移动保持 1:1，不缩放玩家身体/步长，不在走动中旋转或平移整个房间以绕开边界。
- 优先复用同一现实活动区布置各个房间，选择与用户当前实际位置匹配的入口姿态；不满足活动区条件时暂停进入并给出明确恢复步骤。
- 系统安全边界保持可见。若工程无法取得可靠的边界几何，不声称可以自动验证；使用部署时实测并配置的活动区，记录其来源和适用设备。
- 场地适配仅需部署配置，不自动恢复 MR 扫描或管理员标定主线。
- 当前洗消室外轮廓约 15.8×7.6 m、六站路线约 32.32 m，来源为 [C09 房间规格](VR_ROOM_C09.md)及[路线绑定记录](VR_ROOM_PATH_BINDING_C09.md)；这些是虚拟模型数据，不是实际场地测量。
- D03已确认“实际场地未定”。可开发转场、内容和房间灰盒；不得填写假定的最终场地尺寸、冻结最终房间布局或宣称全房间实际可达。门口同样属于必须实际到达的位置。
- 若场地容纳不了原房间，先提出能保留业务关系的活动区重排方案；室内分段传送、缩成桌面模型、放大步长或删站均不是已获授权的替代方案。

### 4.3 房间内导航和面板

每个房间有自己的模型、地图坐标和小精灵路线。开场与对话停留点落在本房间有效路径上；找不到返回路线就暂停提示，不穿模型直切。仅突出当前目标，保留已确认的主动继续/离站。

普通面板沿用约前方 50 cm、眼下 18 cm的初始布置，面对用户后锁定。翻页、重试和提示刷新不得重新贴脸。文档细节可在固定特写面板阅读，但任务结束回到同一室内位置，不利用特写实现室内移位。

## 7. 课程、证据和会话规则

课程采用“旅程 → 房间 → 教学站 → 任务 → 证据”的组织关系。房间数量、教学站数量、任务数量、标注数量和记录字段数量互不等同，不能沿用固定五课、三选项、三证据卡的限制。

需要支持的任务表达包括静音对话、三维观察/必要对象操作、图片区域教学、记录字段核查、本地视频、人员部位教学、产品/资料关联；现有排序、图片判断和台账对账按内容映射保留，不强制给每个知识点附加选择题。

已确认双模式（D05）：

- 带教学习：小精灵逐步介绍对象和方法，可高亮当前教学对象；N04关门、N05设备标注和N08部位高亮按教学目的出现。
- 独立核查：学员自行查看现场和证据、记录发现及判断；提交前不高亮异常位置、不显示正误或把操作示范变成答案。只给输入和阅读帮助，不替学员判断。
- 两模式共用房间和同源证据结构，风险内容通过实际对象/资料状态体现；同一情境不能同时缺少设备又把该设备的正常记录作为无条件合规证据。
- 独立核查按独立检查条件记结果，允许一个对象关联多个发现；完整正常材料也要能支持“未发现问题”。不限制固定风险比例或题数。
- 独立核查在最终办公室统一提交，途中可以回查和修改；带教模式按步骤讲解。模式之间不共享当前答案、提示状态或已提交结果。
- 教学中的“纠正关门”等动作不作为独立核查的预先提示或必做纠错。核查使用本次情境的原始状态与证据版本，必要的开柜/翻页不会清除原风险或改写答案；若对象操作会改变检查条件，记录观察时状态并明确判断依据。

- 每个任务声明完成依据：阅读后主动继续、所需区域逐项查看、门达到目标状态、核查提交等，不能用统一“看过=答对”。
- 任务状态至少区分未开始、进行中、已完成、已跳过；核查结果另存未提交/正确/待修改。不可用资源记为阻断原因，不冒充跳过或完成。
- 带教允许明确跳过；独立核查允许暂留未答后继续到其他房间，结果中列明跳过、未答和漏检，均不计为正确（D07）。跳过不自动点击离开或切换房间。
- 房间状态由必修任务及其明确处理结果汇总；“房间流程结束”和“全部要求已掌握”不是同一结论。
- 复访保留证据查看和作答记录，防止重复计数；独立核查在办公室统一提交前可修改，提交后只读复盘（D08）。重新开始新会话清空当前答案、提示、对象情境与汇总。
- 同一镜号、模拟患者标识、产品、日期、批次及报告在办公室与现场共用同一证据记录；截图、三维标签、表格和结果页从同一数据生成或校验一致。
- 正式内容资源缺失、来源未核实或判定规则未定时，开发版本可以明确占位，正式完成检查必须阻止把它算作通过。
- 应用每次重新启动都创建新进度；不保存跨重启会话，不显示“继续上次”入口，不恢复上一次的房间、答案、抓取、位姿或结果（D06，按用户最后补充）。房间切换与复访在同一次运行内保留会话；同一进程的短暂暂停/摘戴先暂停交互，恢复追踪后继续本次进度，不等同于重新启动。

### 7.1 复访、统一提交与新进度

主线首次到访仍按D04顺序。允许的复访通过已到达房间的门口目的地选择执行，入口同样要求实际走到门口再近触；不打开一个随处传送的地图。复访结束可从该房间门口回到当前主线的续接房间，防止回查打乱首次推进进度。

独立核查在最终办公室展示检查汇总与未答数量，学员可继续回查，或明确统一提交。提交前不展示正确答案；提交后冻结本次判断和情境版本，结果区分正确、漏检、误报、原因错误与未答，并提供只读依据。阅后复访不再修改或重复计数。

带教模式可逐项提示和解释，最终汇总显示已学与跳过；完成学习不等于完成独立核查。双模式各自从新会话开始，切换模式时清空正在进行的另一模式状态。角色形象、静音、交互和本地媒体配置不属于学习进度，无需为“每次重启新进度”重复导入资源。

继续使用当前 `app`、Visitor入口和模板组件，不恢复旧CircleLesson主线，不同时修改目录联接指向的另一条路径。

| 职责 | 目标边界 | 现有证据与迁移点 |

| 旅程配置/会话 | 决定当前房间、教学站、任务和进度；同次运行内存保存，每次应用启动新建；不依赖植物ID或固定数量 | `ClinicalCourseScenes`和`ClinicalCourseCatalog.Load()`当前限制五个后续课程及固定ID；增加旧配置适配，避免一次重命名破坏模板绑定 |

| 资产与内容发布检查 | 核对房间/站点/任务/证据引用、来源、场地及正式资源完整性 | 扩展现有发布与静态检查工具；旧C09检查保留独立配置，不能把新完整稿仍硬校验为六站十二项 |

新配置的最小数据契约（描述要求，不预先锁定类名或Unity加载技术）：

| 对象 | 必需信息 |
| --- | --- |
| Journey | 版本、入口、房间顺序或有明确条件的转移、模式、最终结束条件 |
| Room | 稳定ID、环境资源、活动区、入口、地图/模型版本、教学站、可到达的后续房间 |
| Station | 所属房间、路线锚点、交互锚点、任务列表、结束后的引导 |

| Evidence | 稳定ID、模拟/真实来源标记、可读内容、关联对象、时间范围、适用依据 |

配置检查至少拒绝：重复或悬空ID、不可达必修房间、无出口且非结束节点、任务引用缺失、错误模型/路线组合、字段核查无完整材料、未知任务模式，以及正式版本使用未完成占位资产。不得通过不声明的运行时默认值静默补成“完成”。

资源策略按用户最新明确要求，**只加载当前活动房间，不整包加载，不默认预加载下一房间**。切房按“收起交互和媒体→淡出→卸载旧房间实例与该房间独占资源→确认释放→加载目标→验证→淡入”串行处理。未来如要改为双房间短暂重叠预加载，须先提出实测内存依据并另行确认，不能作为本计划自动优化。隐藏渲染器、SetActive(false)和仅Destroy实例不代表网格/贴图已释放，必须释放资源句柄并核查卸载后的引用和内存。具体加载适配使用现有Unity能力，不为此默认引入新包。

沿用现有规格的工程目标作为待测预算：72Hz下应用帧耗时CPU/GPU P95各不高于13.9ms；冷启动至可交互目标≤15秒、普通切换目标≤5秒；完整最长路线且不少于20分钟无崩溃或卡死。加载单独计时，逐房间记录实际应用帧率和内存；数字是验收目标，不是本次测量结论。场地与内容正确性不能为达成指标而被静默删减。

## 12. 完整体验流程（v2执行设计）

以下顺序是按新稿主线、旧稿补项及现有模型制定的工程编排；除已实现切片外均为待实现目标。门位置与站点坐标须由实物几何和实际活动区共同决定，不将示意顺序直接转成穿墙直线。

```text
大厅：手掌开场 → 安小卫简报 → 选模式 → 实际走到门口
  ↓ 近触切房
办公室：整体观察 → 电脑记录 → 纸质台账/产品档案 → 房间小结 → 门口
  ↓
储存库：柜外 → 开柜与悬挂状态 → 镜体表面 → 柜侧记录 → 门口
  ↓
候诊区：座椅布局 → 实体隔断 → 两侧通道关系 → 门口
  ↓
诊疗区：消化室（设备/报告/记录/台面及废物）→ 门口切换
        呼吸室（对应对象和本室证据）→ 区域小结 → 门口
  ↓
洗消室：隔断与关门 → 工位/分设 → 设备与毛刷 → 用水/指定视频
        → PPE六部位 → 产品与资料 → 附件包装/逐次测漏 → 门口
  ↓
原办公室：汇总 → 可回查修改 → 明确统一提交 → 只读复盘 → 结束
```

### 12.1 大厅与两模式进入

- 保留开场同款安小卫/魔法书发光手印与完整手掌操作步骤，首次可靠追踪固定入口；不是以切换房间重播整个开场。
- 开场分操作提示、简报、选择模式三段。简报解释“点位、方法、依据条款、法律责任”；具体法律文本无来源时不展示编造责任。
- 模式选择为“带教学习”或“独立核查”。两模式均将已读简报作为非评分引导事件记录，不能独立模式遗留N00未答而扣分。切模式只在明确重新开始时创建新会话。
- 完成选择后主动跟随向导去门口；近触前往办公室。大厅可接用户高斯小样，但先验证格式/平移观察/遮挡/性能；不以接入不明格式为由删除大厅流程。

### 12.2 办公室：两次访问、同一房间

首次：`OF-00`整体观察 → `OF-01`电脑 → `OF-02`测漏 → `OF-03`生物学监测 → `OF-04`消毒剂监测与产品档案 → `OF-05`培训与六类资料总核查。

- OF-00为场景观察子组，不挤占新稿“办公室五关”：能看到办公桌、文件柜、打印机、电脑；文件与柜门状态可查。现有OfficeRoom有多工位与椅子，选定一个主核查工位，其他工位不强制重复核查。柜子/打印机是否有可用实体需逐对象确认。
- 走到真实电脑前，近触屏幕进入操作；实体屏与放大视图读取同一记录数据，登录画面只作外观，不增加真实账号验证。蓝白医院系统样式，不能把大块深色问题卡当作最终电脑。
- OF-01按日期/镜号切换至少一个完整样例与一个可从全表判断的训练情境。四组内六字段单独有锚点：日期、患者标识、镜号、开始时间、结束时间、人员。显示查询范围和总条数，不能截掉字段后冒充缺项。
- 文件资料在电脑或实际文件夹上进入固定可读视图；六类材料均有正文、来源/模拟标识、范围、对象编号；“打开封面”不是“核查完成”。产品档案与洗消瓶体共享产品ID，不能把未核验瓶身文字当真实备案。
- 带教依次示范如何查；独立核查能自行选择资料和记录发现，提交前不标红缺失、不提示正确答案。对跨房核查疑点保存证据引用，允许后续回来修改。
- 最终访问不复制办公室：入口选择“查看本次汇总”或“继续核查本室资料”，进度留在本次内存会话。统一提交须显示未答、主动跳过、内容不可用分别的数量并二次明确确认；开发版本有不可用项时只能结束本次开发体验，不能给出完整培训合格结论。

### 12.3 储存与候诊

- 储存柜入口→柜门近触/把手操作→柜内壁/干燥/通风构造→内镜悬挂→镜体局部→柜侧连续日期登记→小结。实际开柜与“已观察”分别记录。当前胃镜是盘绕形态，不能把整个模型旋转90度就声称实现竖直悬挂；竖直镜体几何需另行整理。盘绕资产可先用于表面/标签特写。
- 储存异常需由材质或对象状态显现：内壁水渍、镜体污渍、悬挂异常分别是子条件；缺失资产时逐项预留，不统一算ST-01正确。每周记录作为脚本情境组织完整时间范围，正式标准适用性另核实。
- 候诊入口→座椅观察位→隔断观察位→通道两侧关系观察→小结。用物理隔断与可辨通道表达；无人物模拟，不以红绿箭头替代几何。柜/椅可从现有资源拆取，但用途和尺寸核对后才能使用。

### 12.4 诊疗区：两间实体空间

- `R04_CLINICAL`是汇总区域；目标运行房间为`R04_GI`和`R04_RESP`。可基于同一个原始房间制作两个独立实例，但必须有各自用途、房间ID、设备归属、报告与记录，不将共用一间的两个标签伪装成分室。
- 每室路线：入口/用途→床、设备台和内镜主机→墙上环境报告→后台历史记录→台面耗材与器械分区→废物桶盖→门口。相同检查方法可简化重复讲解，但不同房间的证据不能自动通过。
- CL-01区域条件在两室均有独立几何、设备归属后才能判断；CL-02报告的日期、场所、结果及适用依据独立可读；CL-03时长来自同源起止时间并关联具体产品条件，不能套用通用分钟数；CL-04拆成分区和桶盖两项。
- 当前JSON只有R04_CLINICAL：实施时须一次迁移房间目录、转移边、子任务归属、会话汇总和测试；不得只改文案。所有复访仍从门口发起，不移动现实中的人。

### 12.5 洗消：新稿主线＋旧内容去重

- RE-01：全室/实体隔断→自行回头看门→把手操作→门体实际角度与关闭状态→不同系统槽/机分设→五工位与单向流。开关门教学和换房按钮互不触发；旧门拆件仅在核实其对应本室门后使用。
- RE-02：到清洗台，固定文档原图或已核实设备图，逐项对象与标签对应，可回看。两份新稿设备清单取覆盖并集暂列待核实：压力水枪、压力气枪、测漏仪、灌流器、超声清洗器、运送容器、毛刷；保留各条来源，不称为已核实法规清单。毛刷完整/损坏需要可见差异。
- RE-03：实际水路→水源资料→滤膜外壳近触→参数/维护记录→水槽触点播放新稿指定4:46–5:06本地静音片段→主动返回。外壳/参数/记录/视频分开验收；视频失败可重试，不能以旧40秒视频代签。
- RE-06：人员模型近触→固定特写→衣/围裙、口罩、护目镜或面罩、帽子、手套、鞋六组依次高亮→主动返回。人物资产缺失时保留此任务并注明，不把参考图说成三维人物成品。
- RE-04：产品存放区→已导入带标签消毒剂抓取/转看→可读标签→说明书及办公室同源档案；材料真实性/临床适用性待核验。模型不强制染色，不覆盖用户原FBX/标签。
- RE-05拆成附件包装与逐次测漏两个子组：盒、附件、包装和完整标识；设备、给定使用清单与逐次登记。不能一题通过就同时覆盖两组。
- C09复用：P01保留“操作教学→单独练习→显式开始正式观察→逐个小光圈→主动图解/回看→结束收镜”，已有4倍镜片和固定取景窗不退化；P02工序/处置、P03设备观察、P04毛刷/水路、P05产品、P06记录分别映射RE子项。只有对象/证据/完成条件一致才复用结果，N04实物门、N07指定视频、N08人物不能由旧课程完成代签。正式合并后不让学员被迫完整学习两遍。

### 12.6 全程统一状态

`进入房间 → 静音任务导入 → 向导沿路线带路 → 到站 → 操作/观察/查证 → 主动继续或明确暂留 → 房间小结 → 引导至门 → 近触切房`。

一个主教学界面可见；切房前关闭所有媒体/特写并取消抓取。丢手只暂停手部交互，丢可靠头追踪冻结空间推进；恢复不重置本次房间。课程复访恢复已看证据与检查结果，不恢复旧手坐标或抓取。应用重启不读取上次进度。

## 13. 资产导入、布局与视觉契约

模型优先级：用户已处理资产→本次Models.zip可用几何与材质→剧本图对应内容→缺口新制。只要求用户做大厅高斯一个样本；办公室/诊疗室取消高斯制作请求。

资产五级状态：`已收到 → 已导入/可加载 → 已整理/预览 → 已绑定运行房间 → 内容和Quest验收`。不可跨级描述。原文件保留在`app/_IncomingModels/Models.zip`，选取源文件导入`Assets/EndoscopyTheme/ImportedModels/Source/`，派生Prefab与材质在`ImportedModels/Prepared/`。它们不在Resources、未被Visitor引用时不自动进入主线；原洗消和消毒剂路径保持。

- 本轮整理Prefab将底部/水平中心归零；房间不缩放，家具/胃镜只作展示比例校准，记录倍率。包围盒不是实际净活动区，房间底部也可能是楼板底而非行走面，发布前必须另定floorAnchor。
- 原材质可用则保留；不兼容材质生成URP副本，缺外部贴图必须注明。源模型灰白预览不是最终视觉，需补材质并与剧本参考图片核对。家具不可用灰盒长期代替，医用标签不可生图后直接充当正式证据。
- 不将完整BIM的6100个网格直接等同于交互对象。先按墙/地/顶/门/家具/设备语义分组，保留要交互的独立门扇/器物，静态部分简化/合并；不在测试前承诺固定降面比或自动LOD已达标。
- 房间外观资源、简单碰撞/路线障碍、交互锚点分开制作但共用同一坐标基准和版本。不可修改源房间后继续使用旧路线哈希。

- 高斯只作为可替换视觉适配方式，玩法/证据/门/碰撞仍使用Unity对象；在Quest立体渲染、透明排序、内存与帧耗未验证前不承诺可以直接使用。
