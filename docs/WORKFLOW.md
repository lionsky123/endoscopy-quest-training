## 规格 → 设计 → 计划 → 验证

### 规格：明确本次可观察结果

使用 `spec-driven-development`，先定位已有规格和矩阵行。记录目标、输入依据、范围、验收条件及尚未核实的事实。沿用既有完整路线与单一引导学习决定；不因切换工作流重写产品目标。

涉及多个独立能力的新需求才补能力表，列稳定编号、职责、依赖和提供方契约。已有 M/C 编号用于现有工作包，不重新编号或伪装成新需求。

### 设计：让实现依据可检查

在相关规格章节或原计划当前任务旁补充设计。只有需要独立维护的跨模块决策才新增 ADR；只引用仍有效的历史决定。

每个 VR 内容任务需要说明：

- 对应剧本/矩阵条目，以及体验者在该步骤要观察、查阅或判断的内容。
- 使用的房间、观察位、实体对象和资料载体；资源源文件、正式消费者及共用数据关系。
- 手部操作、成功/失败反馈、跳过/未答、回查和提交后状态；文案与开发信息的分离。
- 当前房间资源的创建、解绑、销毁和释放边界；失败重试时如何恢复。
- 如何分别验证规则、真实 Play、实际画面和 Quest；尚缺依据或资产明确列出。

模板中只保留本次相关项。纯文档任务不设计运行时交互、不要求 Unity 测试或生图。网页 UI 技能不自动套用于 Unity VR；设计接口契约时才按需使用 `api-and-interface-design`。

### 计划：在原任务下切出可验收增量

使用 `planning-and-task-breakdown`，按依赖安排任务，优先闭合一个可观察行为及其证据。单任务通常涉及 1–5 个文件；更大工作按行为分解，不为满足数量人为切碎资源与消费者。

任务模板：

```markdown
- [ ] Cxx.a 具体可观察结果
  - 依据：规格章节 / 矩阵条目。
  - 依赖：前置任务；无则写“无”。
  - 设计与文件：本次方案、实际资源或待修改文件。
  - 验收：明确行为、错误路径及完成边界。
  - 验证：适用层级、真实命令或人工检查方法。
  - 证据：报告路径、结果和仍未满足条件；验证前保持空缺说明。
```

原计划存在同一项时就地补充，不复制到其他清单。并行工作只安排无共享写入冲突的任务；跨模块接口先确定。已有业务任务的未勾选状态不因文档迁移改变。

### 验证与交接：按证据结束任务

编译门槛、测试频率和验收分工统一遵守[根规则第7节](../AGENTS.md#7-编译测试与验收)。下表用于选择证据，不是每轮自动执行清单。

| 变更 | 所需证据 |
| --- | --- |
| 纯文档 | 本地链接、现行/历史身份、规则一致性、差异范围 |
| 代码、程序集、包或编译相关配置 | 当前 Android 目标下 Unity 实际导入/编译无错误的结果；编译受阻如实说明，不声称可正常编译 |
| 行为修复 | 故障行为复现、针对性回归；现有计划要求的 red → green 如实记录 |
| 启动或生命周期 | 正式入口真实 Play，覆盖初始化与首帧、释放顺序和失败恢复 |
| 视觉、文案、素材 | 实际渲染及可读、可达、遮挡检查；资源登记与消费者一致 |
| 真实头手、双眼渲染、性能 | 对应安装包身份及 Quest 实测；编辑器不能代签 |

适用检查通过后回填原任务；除非有新改动、失败或未解风险，不反复运行同一组检查。未完成事项说明下一步和阻碍。交接保留任务编号、变更文件、未提交状态、命令/结果、报告路径及所需授权；不把历史聊天中的部署授权自动延续到新任务。

## 常用验证入口

以下从仓库根目录执行。脚本参数已查阅；真实 Play 命令仅用于用户报告相关 Bug 或明确要求检查，不因普通修改自动调用。本次文档整理不运行 Unity。Unity 批处理前确认工程未被已有实例占用，保留脚本内的 Android 目标和独立运行名。

```powershell
git status --short
git diff --check

$taskRun = 'check-' + (Get-Date -Format 'yyyyMMdd-HHmmss')
# 仅当用户报告启动 Bug 或明确要求验证启动时：
powershell -NoProfile -File tools/test_production_play.ps1 -Run $taskRun

# 仅当任务涉及对应行为时，将筛选值替换为已核实存在的测试名：
powershell -NoProfile -File tools/test_inspection_editor.ps1 -Run $taskRun -TestFilter '<对应测试完整名>'
```

这里只列测试入口，不提供自动 APK 构建或设备写入步骤。纯文档验证无需调用以上两个 Unity 脚本。

## GPT-6 与技能适配依据

使用标准 Markdown 标题、直接可执行的项目约束、按任务读取的链接和明确完成条件。根规则保持长期有效，运行状态留在计划和证据中；技能按需要启用，避免把所有技能固定串成流程。已有授权范围内连续推进，真实的新决定才请求用户输入。

参考 OpenAI 官方 [GPT-6 Astra 技能与提示整理建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)及 [AGENTS.md 分层说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。这些是本项目的适配依据，不是模型专用文件格式或模型效果验证声明。
